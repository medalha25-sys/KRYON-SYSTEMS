🛡️ TESTE RLS COM IDENTIDADES REAIS

Plano Técnico do Teste de Isolamento Multitenant (Empresa A vs Empresa B)

Módulo Piloto: Kryon Lava Rápido (kryon-lava-rapido) | Banco Central: Sistemas Kryon (pgpobxvkojawrstadrel.supabase.co)

1. Arquitetura de Autenticação & Separação de Contextos

🔴 Camada 1: Setup Administrativo (Privilegiado)

  • • Criação de 2 identidades descartáveis reais em auth.users:
  •   - USER_A: teste_salinas_a@kryonsystems.internal
  •   - USER_B: teste_estetica_b@kryonsystems.internal
  • • Criação das Organizações A e B (slugs únicos).
  • • Vinculação estrita de membros em organization_members (role: owner).
  • • Inserção dos dados iniciais (serviços, clientes, agendamentos).

🟢 Camada 2: Execução RLS (Não-Privilegiada: role authenticated)

  • • A sessão altera explicitamente o contexto de execução para:
  •   SET LOCAL ROLE authenticated;
  •   SET LOCAL "request.jwt.claim.sub" = '<USER_ID_REAL>';
  •   SET LOCAL "request.jwt.claim.role" = 'authenticated';
  • • Execução dos 8 testes com asserts de PASS/FAIL.
  • • Zero privilégios de superusuário: validação 100% autêntica de RLS.

3. Bloco Principal de Teste com Contexto Não-Privilegiado
-- Exemplo do bloco de execução não-privilegiada no PostgreSQL: PERFORM set_config('role', 'authenticated', true); PERFORM set_config('request.jwt.claim.sub', v_user_a_id::text, true); PERFORM set_config('request.jwt.claim.role', 'authenticated', true); -- Tentativa de leitura cruzada: Usuário A tentando ver dados da Org B SELECT count(*) INTO v_count FROM public.services WHERE tenant_id = v_org_b_id; IF v_count = 0 THEN RAISE NOTICE 'TESTE 03 [PASS]: Usuário A recebeu 0 registros da Org B (RLS OK).'; ELSE RAISE WARNING 'TESTE 03 [FAIL]: Vazamento detectado!'; END IF;
4. Procedimento de Teardown / Limpeza Pós-Validação
Após a conclusão dos testes e a sua aprovação formal, executaremos a limpeza direcionada dos registros de teste em auth.users e organizations, mantendo o banco central estritamente limpo.
